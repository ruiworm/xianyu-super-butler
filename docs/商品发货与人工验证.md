# 密钥、链接一起发货

在「卡密库存」添加批量库存，每一行表示一份完整商品，例如：

```text
KEY-001----https://example.com/redeem/001
KEY-002----https://example.com/redeem/002
```

在新增/编辑库存，或商品的「配置自动发货」、通用规则的编辑窗口中开启「多参数发货模板」：

```text
密钥：{参数1}
兑换链接：{参数2}
请保管好密钥，按链接中的说明兑换。
```

使用多个 `----` 可以继续增加 `{参数3}`、`{参数4}` 等字段。也支持每行一个 JSON 对象：

```json
{"密钥":"KEY-001","链接":"https://example.com/redeem/001"}
```

对应模板使用 `{密钥}`、`{链接}`。固定链接可直接写进模板，用 `{参数}` 插入整行密钥。模板保存到库存，所有引用该库存的规则共享它。商品发货窗口里的「保存此库存发货模板」和「保存发货策略」分别保存模板与库存绑定。

一行中的字段一起扣减，不要把同一份商品的密钥和链接分成两个库存行。缺少任一必需参数时，整单库存不扣减。关闭模板时沿用原来的内容和备注逻辑。API 数据源也可使用模板，但上游已分配的密钥无法在模板失败时自动退回。

通用规则的优先级为商品专属 > 当前账号 > 当前用户的全局规则。同一作用域优先最长匹配关键词；同长度的多个候选仍停止发货，避免错发。已配置新版规格策略的商品仍使用自己的绑定；停用、未绑定或未知规格不会回退通用规则。

商品页面不再提供 SKU 识别、买家接口试探和 SKU 限额配置，也无需填写平台 SKU ID。商品规格与发货库存仍通过现有发货策略配置；历史订单和已保存的规格绑定保留。

# 每个商品的 AI 提示词

入口：「AI 回复」→选择账号→「商品 AI 提示词」。先创建一条提示词，再勾选一个或多个商品。每个商品只关联一条商品专属提示词；编辑这条提示词会同时更新所有关联商品。将商品勾选到另一条提示词时，它会从原提示词转移。原有单商品提示词首次打开页面时会自动保留并转换。账号仍需启用 AI，模型接口在「系统设置 → 默认 AI 配置」设置。

回复时会合并账号通用规则、当前商品规则和订单/议价安全边界。商品规则不影响其他商品或其他账号。留空保存即可恢复只使用账号规则；同步商品不会覆盖提示词。关键词回复仍优先于 AI，可在「AI 回复」页直接配置关键词和对应回答。

系统 AI 接口配置优先于旧账号级配置；系统密钥未配置时，保留使用旧账号密钥。思考等级默认不修改接口参数；关闭和低、中、高需要服务商及模型支持。OpenAI 兼容接口使用 reasoning_effort；模型名称含 qwen 时使用 enable_thinking 和 thinking_budget。Gemini 原生和 DashScope 应用接口不使用这些思考参数。

# 服务器运行，电脑辅助登录/验证

## AI 按买家意图发送固定图片

在「AI 回复」选择账号，开启并配置模型。在「按意图发送固定图片」添加图片规则：

1. 上传一张 JPG、PNG、GIF 或 WebP 图片，最大 5MB。
2. 填写名称和发送场景。例如名称「安装步骤图」，场景「买家问怎么安装、怎么接线，或要求安装说明时发送；只问价格时不要发」。
3. 图片仅适用于某个商品时填写商品 ID，留空则适用于该账号全部商品。同名规则优先使用商品专属版本。
4. 点击「保存图片规则」。添加、停用、修改、移除后都需要保存。
5. 在本页「测试回复」输入买家问法；测试专属规则时填写测试商品 ID。匹配结果会显示图片预览，测试不会发送到闲鱼。

关键词回复优先，未命中关键词才进入 AI。系统只允许 AI 选择已保存、已启用且符合当前商品的图片编号，每次最多一张。匹配不确定、模型输出异常或图片文件丢失时继续普通文字回复。文字模型依据你填写的场景选择图片，不会直接识别图片内容。配置图片规则会增加一次模型意图识别调用；真实识别效果应使用多种买家问法进行测试。

实际发送会通过现有图片上传和消息接口，发送图片消息；上传或发送失败会在回复日志中记录。图片规则随数据库备份，图片文件需要另外保留 `static/uploads` 目录。本项目的三份 Docker Compose 已增加该目录挂载；你现有的手动创建容器需要补充 `/opt/xianyu/uploads:/app/static/uploads` 挂载，并先迁出旧容器中需要保留的图片。单纯重新建容器而不保留此目录会丢失图片文件。

## 桌面登录会话同步

项目现有卖家端请求通过 `utils/xianyu_seller_api.py` 使用 Cookie 直连 MTOP API，消息由 WebSocket 接收。`utils/xianyu_utils.py` 的 `generate_sign()` 使用 `MD5(token & t & appKey & data)`，其中 `token` 来自 `_m_h5_tk` 下划线前的部分，请求参数名为 `sign`。这里不是 HMAC-SHA1，也不能据此承诺永久免验证；正常 API 调用仍可能返回平台风控。

桌面同步补充会话来源：Cookie 更新后使用现有账号任务重新连接，再继续 API 和消息业务。普通令牌过期沿用现有响应 Cookie 更新、重新签名重试流程；平台要求人工验证时应完成验证后同步新会话。

日常默认关闭周期性的浏览器 Cookie 刷新，保留 API 令牌续期和消息心跳。旧逻辑会在启动后立即进行浏览器刷新，并暂停心跳，可能造成额外断线；现在即使显式开启浏览器刷新，也会等待完整刷新间隔，并保持心跳。人工验证或风控冷却期间跳过周期性浏览器刷新。如确需恢复此定时功能，可设置 `BROWSER_COOKIE_REFRESH_ENABLED=true`。扫码登录及实际触发验证时的处理入口仍可使用。

Cookie 解析兼容分号后有空格和无空格的格式。刷新令牌前会从数据库的 `value` 字段读取最新 Cookie，避免因读取不存在的字段而继续使用旧会话。

管家仍部署在服务器，Windows 电脑运行闲鱼卖家客服和本项目的桌面连接工具。在「账号管理 → 桌面客户端接入」生成该账号的专属连接令牌，下载工具，解压后双击 `start.bat`。电脑需安装 Python 3.11 或更新版本（带 tkinter）；首次启动会安装工具自己的依赖。

在工具中填写管家地址、连接令牌，选择客户端的 `.exe`。先完全退出客户端（包括托盘），再点「启动客户端并连接」；如果已用本机调试端口启动，可点「连接已启动客户端」。随后在客户端登录、手动完成平台要求的滑块。连接工具保持运行时，会检测稳定会话并自动上传，无需每次复制 Cookie。

客户端须支持 Chromium 的本机调试连接。工具通过启动参数请求在 `127.0.0.1` 开放调试端口，默认 `9222`；若当前版本不支持、已有进程未退出或没有可用闲鱼页面，会提示具体连接问题。工具不修改客户端安装文件，也不模拟滑块。真实 Windows 客户端版本的兼容性仍需在电脑上检测。

服务器会核对新旧会话的 `unb` 身份标识，缺少必要字段或账号不一致时拒绝更新。成功导入会更新数据库和运行任务，允许账号重新连接。导入成功只表示会话已保存，平台是否接受新会话应以实际连接状态为准。

后台可以查看最近连接、最近同步和令牌到期时间，也可随时撤销连接。令牌用于绑定账号的会话同步及已开启的桌面查询，不能用于管理其他账号。有效期为 90 天，重新生成后旧令牌立即失效；工具关闭后需要重新填写令牌。服务器只保存令牌哈希，工具不把令牌和 Cookie 写入文件。会话没有变化时仅报告在线状态，不重复重启账号任务。

远程地址使用 HTTPS。若服务器暂时只有 HTTP，可在 Windows 终端建立 SSH 隧道（终端需保持打开）：

```powershell
ssh -N -L 127.0.0.1:38889:127.0.0.1:38888 ubuntu@<服务器IP>
```

然后用 `http://127.0.0.1:38889` 打开管家，连接工具也填这个地址。该命令不开放新的公网端口。若服务器 SSH 地址、端口或管家端口变化，按实际情况调整。

接入窗口的「手动导入」仍可粘贴自己的完整 Cookie。若开启「商品和订单通过电脑客户端查询」，商品列表/详情、卖出订单列表/数量及订单详情会通过客户端页面已有的 MTOP SDK 执行。客户端必须同时提供本机调试入口和可访问的 SDK；能力状态显示「已就绪」后可在管家商品或订单页面发起同步。客户端离线或接口不可用时明确失败，不自动回退服务器直连。

未开启此选项时沿用服务器查询。消息收发和发货等其他操作仍在服务器，不能将此功能称为全部业务接管。具体客户端版本仍需 Windows 实机验证；平台可能再次要求手动验证。详见 [连接工具说明](../desktop_bridge/README.md)。

服务器必须运行包含这些变更的新代码镜像。当前上游 `v3.3.0` 预构建镜像不会自动包含本仓库的改动；仅更新宿主机目录也不会改变该容器中的代码。部署前保留 `/opt/xianyu/data`、`logs`、`backups` 的现有挂载并备份数据库，使用本仓库构建镜像后再替换容器。不要直接使用默认 Compose 文件另起一个空数据目录的实例。
